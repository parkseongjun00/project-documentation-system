| 항목 | 내용 |

---

## 0. 일러두기

- 이 문서는 문서를 선택하고 서로 연결하는 공통 기준이다. 실제 프로젝트 내용은 해당 기준 문서와 기록에 작성한다.
- 공통 표현·서식은 [WritingGuide.md](WritingGuide.md), 개별 문서의 고유 규칙은 해당 문서의 일러두기, 기록 파일의 공통 절차는 해당 폴더의 README에서 관리한다.
- 기존 문서나 이슈 트래커가 같은 책임을 맡고 있으면 4.1절에 따라 실제 위치를 연결한다.

### 1.2 문서별 책임과 경계

| 문서 | 담당 범위 | 갱신·보존 방식과 경계 |
| --- | --- | --- |
| ProjectSpec | 문제와 목표, 현재 동작 규칙과 제약의 기준 | 현재 유효한 기준을 갱신하고 미정 사항을 구분한다. 기능 목록과 구현 순서는 각각 Systems·DevPlan에서 관리한다. |
| Systems | 기능 범위와 대표 입력·출력 | 필수와 선택 후보를 구분한다. 상세 동작·예외는 ProjectSpec으로 연결하며, 표 순서는 우선순위가 아니다. |
| DevPlan | 필수 작업의 순서와 선행 관계 | 합의한 순서·착수 조건을 갱신한다. 기능 설명은 Systems를 참조하고, 작업별 검증은 논의 초안이나 검증 계획·보고에서 다룬다. |
| DevNotes | 주요 판단과 그 이유 | 당시 의미·사유·검증 범위를 보존한다. 판단 변경은 후속 기록으로 남기며, 의미를 보존하는 편집·압축은 공통 규칙에 따라 허용한다. 현재 명세를 대신하지 않는다. |
| Backlog | 사용자 요청이나 등록안 동의로 정한 재검토 과제 | 보류·착수와 처리 결과를 관리한다. 개발 계획·아이디어·미완료 검증을 자동 등록하지 않는다. |
| HANDOFF | 세션 간 공유할 현재 상태와 다음 작업 | 라운드마다 작업별 본문을 교체한다. 지속적으로 참조할 지식은 기준 문서나 보존 기록으로 연결한다. |
| DiscussionDraft | 한 세션의 가장 최근 요청에 대한 작업 메모 | 필요한 경우에만 사용하고 새 요청에서 작업별 본문을 교체한다. 다른 세션의 공통 정보원이나 영구 근거로 사용하지 않는다. |
| Troubleshooting | 특정 문제의 조사 경로 | 문제별 파일에 가설·시도·결과·판단을 이어 쓴다. 실패 경로를 보존하고, 확정된 주요 결정의 상세는 DevNotes로 연결한다. |
| WritingGuide | 여러 문서에 공통인 작성 형식 | 문서 편집 시 확인한다. 문서 고유 운영 규칙과 항목별 작성 안내는 대상 문서에서 관리한다. |

## 2. 공통 운영 원칙

### 2.1 정보의 원본과 참조

- 하나의 사실·결정은 담당 문서 한 곳에 자세히 기록하고, 다른 문서는 필요한 요약과 원본 링크를 제공한다.
- 문서 지도·범위 요약·변경 이력처럼 요약 자체가 목적인 반복은 허용한다. 요약은 원본과 일치시킨다.
- 문서 간 역할과 정보 이동은 이 문서에서, 공통 표현은 WritingGuide에서, 고유 운영 규칙은 각 문서에서 관리한다.
- 개별 항목의 입력 방법은 해당 절의 작성 안내에 둔다. 기록 파일이 공유하는 절차는 폴더의 README에 두고 파일마다 반복하지 않는다.
- 참조가 있는 내용을 옮기면 링크를 함께 갱신한다. 보존할 판단과 근거가 담당 위치에 있는지 확인한 뒤 중복 설명을 줄인다.

---

### 2.2 출처와 확정 상태

- 관찰한 사실, 사용자 의견·결정, AI 제안, 미확인 사항을 구분한다. 사용자가 동의하기 전의 제안을 확정 기준에 조용히 반영하지 않는다.
- 기준 문서에는 현재 유효한 내용을 중심으로 쓰되, 미정 사항과 선택 후보는 관련 절에서 확정 내용과 구분한다.
- 보류 과제의 등록은 [Backlog의 등록 규칙](Backlog.md)을 따른다. 어딘가 기록하라는 요청이나 문서 편집 승인을 백로그 등록 승인으로 해석하지 않는다.

---

### 2.3 현행 기준과 판단 이력

- ProjectSpec·Systems·DevPlan은 현재 합의된 기준·범위·순서를 관리하고, DevNotes는 당시 판단과 이유를 보존한다.
- 장기적으로 필요한 사유·제약·기각 이유는 삭제하지 않고 기록에 압축해 남긴다. 애초에 사용자가 설계한 적 없는 것으로 확인된 개념은 사유 서술 없이 삭제할 수 있다.
- 결정이 바뀌면 현재 기준과 후속 결정 기록을 함께 정리한다. 이전 기록의 의미와 당시 검증을 보존하는 구체적인 편집 방법은 [DevNotes 공통 규칙](DevNotes/README.md)을 따른다.
- 현재 구현이 승인된 기준과 다르면 구현 사실·문서 기준·영향을 정리하고 후속 기록을 확인한다. 기준 유지·변경·판단 보류 중 정해진 방향과 승인 범위에 맞춰 반영한다.
- 미구현·후순위 항목이나 과거 판단은 기록 시점과 범위를 함께 살펴 현재 기준과의 충돌 여부를 판단한다.

---

### 2.4 임시 정보와 보존 기록

- HANDOFF와 세션별 논의 초안은 작업별 본문이 교체되는 문서다. 계속 참조할 결정과 근거는 기준 문서나 보존 기록에 남긴다.
- 임시 문서의 본문·특정 절을 영구 근거로 연결하지 않는다. HANDOFF는 현재 작업의 진입점으로 안내할 수 있고, 논의 초안은 역할 안내에 파일명을 적을 수 있다.
- 확정 전 논의·계획은 대화나 해당 세션의 초안에서 검토한다. 확정 뒤에는 내용의 책임에 따라 명세·범위·순서·결정 기록에 반영한다.
- 보존할 정보와 실제 기록 위치를 확인한 뒤 임시 본문을 교체한다. 과거 본문은 Git 이력으로 확인하며, 논의 초안의 과거 내용은 버전 관리에 포함된 경우에만 남는다.

## 3. 작업 흐름과 문서 갱신

### 3.1 요구사항과 작업 계획 수립

1. 과제 원문이나 사용자 요청에서 문제·목표·요구사항·제약·제출 조건을 확인하고 ProjectSpec에 정리한다.
2. Systems에 필수 기능과 선택 후보의 범위·대표 입력·출력을 작성한다.
3. DevPlan에 필수 작업을 나누고 선행 작업·착수 조건을 정한다. 독립적인 작업은 병행할 수 있다.
4. 논의가 길거나 정리된 문서를 요청받으면 세션의 논의 초안을 사용한다. 확정한 새 판단은 DevNotes에 남기고, 이어받을 작업이 있으면 HANDOFF에 요약한다.

---

### 3.2 구현과 검증 결과 정리

1. 인계받는 작업은 HANDOFF에서 현재 상태를 확인하고 관련 기준 문서와 실제 코드·자산을 대조한다.
2. 작업별 검증 계획에 대응 요구, 입력·조건, 확인 방법과 기대 결과를 정한다. 준비 작업은 지금 확인할 산출물과 이후 동작을 확인할 작업·방법을 명시한다.
3. 작업 중에는 관련 요구를, 최종 검토에서는 전체 필수 요구를 과제 원문과 대조한다. 원문이 없는 작업은 사용자 요청과 기준 문서를 사용하고, 접근하지 못한 자료는 미확인으로 남긴다.
4. 완료 보고나 담당 논의 초안에 요구별 근거 위치·실제 결과·미충족 및 미확인 사항을 남긴다. 사용자가 먼저 볼 위치와 다시 확인하는 방법도 제시한다.

담당 세션은 작업별 검증 계획·결과를 [논의 초안 양식](DiscussionDraft.md)의 작성 안내에 따라 정리할 수 있다. 다른 세션은 담당 초안 대신 HANDOFF와 보존 문서에서 필요한 결과를 확인한다.

---

### 3.3 기준 변경과 결정 기록

1. 변경할 기준, 이유, 영향 범위를 확인하고 승인된 범위를 정한다.
2. 동작 규칙은 ProjectSpec, 기능 범위와 입력·출력은 Systems, 순서·착수 조건은 DevPlan에 반영한다.
3. 확정된 주요 판단은 DevNotes에 문제·결정·근거·검증과 한계로 보존한다. 이전 판단이 바뀌면 해당 기록에 후속 변경을 안내한다.
4. 조사 경로가 남아 있으면 Troubleshooting에 보존하고 최종 결정 기록으로 연결한다. 다음 작업에 필요한 결과는 HANDOFF에 요약한다.

예를 들어 기능의 동작 규칙을 바꾸기로 합의했다면 ProjectSpec에 현재 규칙을 반영하고, DevNotes에 변경 이유와 검증·한계를 남긴다. 기능 범위나 작업 순서도 바뀌었다면 Systems·DevPlan을 갱신한다.

---

### 3.4 작업 인계와 후속 과제 관리

1. 이번 작업에서 계속 보존할 기준·결정·조사 결과가 담당 문서에 반영되어 있는지 확인한다.
2. HANDOFF에 현재 상태, 확인한 결과, 미확인 범위, 다음 작업의 시작 조건·순서·완료 판단과 관련 원본을 요약한다.
3. 병행 작업은 각 세션이 자기 초안을 관리하고 통합을 맡은 세션이 공용 HANDOFF를 갱신한다.
4. 나중에 다시 다룰 과제는 사용자가 백로그 등록을 요청하거나 등록안에 명시적으로 동의했을 때만 등록한다. 미완료 검증과 남은 작업은 우선 해당 검증 보고·인수인계에 남긴다.
5. 백로그에서 실제 관리한 과제의 완료·철회 결과는 처리 표에 요약하고 필요한 보존 기록을 연결한다. 등록 취소·완전 삭제는 Backlog의 규칙에 따라 참조까지 정리한다.

## 4. 프로젝트 적용

### 4.1 기존 문서와의 역할 대응

- 도입 시 현재 기준, 작업 순서, 판단 이력을 각각 어디서 관리하는지 확인한다. 기존 문서가 같은 책임을 맡고 있으면 이름을 유지하고 1장의 문서 지도에 실제 위치를 연결한다.
- 기본 문서 세트를 함께 사용하되, 직접 복사할 때는 필요한 문서를 선택하고 상대 링크와 책임의 연결을 확인한다. 사용하지 않는 역할도 기존 문서·도구에서 담당하는지 명시한다.
- 보류 과제의 위치는 처음부터 마련한다. 기존 이슈 트래커가 같은 역할을 맡고 있으면 그 위치를 연결하되 백로그 등록 조건은 유지한다.
- 여러 세션을 오가는 작업에는 HANDOFF를 사용한다. 논의 초안은 필요할 때 세션별로 사용하고, 긴 개별 문제의 조사는 Troubleshooting에서 관리한다.
- DevNotes·Troubleshooting의 공통 규칙과 색인은 각 폴더의 README에 둔다. 세션별 초안의 버전 관리 포함 여부도 정한다.

---

### 4.2 작업 지침과 참조 경로 구성

문서 복사와 AI 작업 지침 연결을 구분한다. 대상 프로젝트에서 실제 적용되는 AGENTS.md 등에 확인 조건·문서 경로·목적을 짧게 안내한다.

| 확인 조건 | 참조 대상 | 확인 목적 |
| --- | --- | --- |
| 문서 체계를 처음 파악하거나 기록 위치를 판단할 때 | 대상 프로젝트의 DocumentationSystem.md 또는 문서 지도 | 문서별 역할과 원본 위치 |
| 프로젝트 문서를 작성·수정할 때 | 대상 프로젝트의 WritingGuide.md와 대상 문서의 일러두기 | 공통 작성 형식과 고유 운영 규칙 |
| 결정·조사 기록을 편집할 때 | 해당 폴더의 README와 대상 기록 | 기록 절차와 기존 판단·조사 맥락 |
| 다른 세션의 작업을 이어받을 때 | HANDOFF.md와 관련 기준·보존 문서 | 현재 상태와 작업 조건 |

- 기본 문서 폴더가 `docs/`라면 작업 지침에 `docs/DocumentationSystem.md`와 `docs/WritingGuide.md`를 연결한다. 사용자 지정 폴더에서는 실제 경로를 사용한다.
- 스킬 내부의 `docs/`는 배포용 양식 원본이다. 구축 후 작업은 대상 프로젝트의 실제 문서와 규칙을 참조한다.
- 구축용 SKILL은 복사와 참조 경로 확인을, README는 사람을 위한 도입 안내를 맡는다. 지속적인 확인 지침은 대상 프로젝트에 적용되는 AGENTS 등에 둔다.
- 대상 작업 지침에 안내가 없으면 기존 지침을 보존하는 최소 연결안을 제시한다. 실제 지침 파일·설정 변경은 승인된 범위에서만 진행한다.
- 공통 전역 지침 전체의 적용과 프로젝트 문서 안내의 연결은 별개다. 특정 AI 환경의 실제 지침 적용 여부는 해당 환경에서 확인하고 미확인 조건은 보고한다.
