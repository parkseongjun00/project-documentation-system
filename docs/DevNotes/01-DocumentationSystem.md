# 문서 체계 결정

공통 기록 방식은 [개발 노트 안내](README.md)를 따른다.

---

## 1. 문서 체계

### 1.1 여러 프로젝트에 적용할 문서 역할 정의 (2026-11-16)

- **문제**
	- 문서 체계를 다른 도메인에 적용하려면 게임 설계 문서의 역할을 일반화하고 기능 범위와의 경계를 정해야 했다.
- **결정**
	- `ProjectSpec.md`에 문제와 목표, 해결 방향, 동작 규칙과 제약을 담는다.
	- `Systems.md`에 구현 범위에 포함되는 시스템·기능을 정리한다.
- **근거**
	- 상세 명세를 읽기 전에 기능 전체를 훑어볼 수 있고, 개별 동작의 정확한 조건은 해당 명세에서 확인할 수 있다.
- **검증과 한계**
	- 기존 GDD와 기능 목록의 역할을 비교했다. 비게임 사례에 적용한 결과는 후속 검토에서 기록한다.

---

### 1.2 논의 초안을 세션별 파일로 운영 (2026-11-16)

- **문제**
	- 세션들이 하나의 초안 본문을 갱신하면 병행 작업의 메모와 결과가 서로 덮일 수 있다.
- **결정**
	- 세션마다 담당 초안 파일을 두고, 확정 결과를 공통 기준 또는 보존 문서에 옮긴다.
- **근거**
	- 작업 중에는 각 세션이 자기 맥락을 유지하고, 공통으로 필요한 정보는 보존 위치에서 이어 볼 수 있다.
- **검증과 한계**
	- 별도 파일을 쓰는 절차와 예시를 문서화했다. 실제 병행 세션에서의 운영 검증은 남아 있다.
