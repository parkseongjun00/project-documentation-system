# 구현 전 해결 방향과 계획 검토

사용자의 생각·아이디어에서 나온 해결 방향과 계획을 구현 전에 점검한다. 중요한 오해, 가정, 누락과 모순을 일찍 발견해 불필요한 시행착오와 재작업을 줄인다. 사용자가 검토할 쟁점과 진행 속도를 정한다.

## 1. 검토할 생각과 계획 이해

- 사용자의 설명과 제공 자료에서 풀려는 문제, 생각한 해결 방향, 구현 범위와 계획을 파악하고 짧게 확인한다. 사용자가 직접 제기한 질문이나 우려가 있으면 우선 반영한다.
- 관련 근거는 프로젝트의 문서 지도나 사용자가 준 경로에서 찾는다. `ProjectSpec.md`에서 요구·완료 기준·제약을, `Systems.md`에서 기능 범위와 입력·출력을, `DevPlan.md`에서 순서·선행 작업·착수 조건을 확인한다. 같은 역할의 다른 문서도 사용할 수 있다.
- 문서는 이번 판단에 필요한 부분부터 읽는다. 대화만으로 제시된 아이디어도 검토할 수 있다. 중요한 맥락이 부족하면 판단에 필요한 내용을 좁혀 묻는다.
- 과제 원문이나 제공 자료가 있으면 관련 요구를 직접 대조한다. 기존 동작을 전제로 한 계획은 관련 코드와 실제 검증 결과도 확인한다. 자료에 명시된 요구, 사용자 결정, 임시 가정과 AI 제안을 구분한다.

## 2. 구현 후 재작업으로 이어질 쟁점 선택

- 해결 방향이 실제 문제와 필수 요구를 충족하는지, 완료 기준으로 확인 가능한지 살핀다.
- 근거가 부족한 가정, 서로 다른 해석, 문서나 결정 사이의 모순, 계획에서 빠진 선행 조건을 찾는다. 필요하면 구체적인 사용 상황이나 경계 사례로 생각을 점검한다.
- 주어진 환경·시간과 선택한 범위가 맞는지, 첫 작업에 착수하고 결과를 확인할 방법이 있는지 살핀다.
- 답에 따라 필수 동작, 해결 방식, 범위 또는 작업 순서가 달라지는 쟁점을 우선한다. 지금 확인하는 비용과 나중에 잘못을 고치는 비용을 고려하고, 사용자가 정한 우선순위를 따른다.

## 3. 질문과 선택지 제시

자료와 도구로 확인할 수 있는 사실을 먼저 찾는다. 확인한 내용과 근거를 짧게 정리하고, 사용자의 판단이 필요한 쟁점을 좁힌다. 접근할 수 없는 자료나 아직 확인하지 못한 사실은 미확인으로 표시한다.

- 문서에 이미 결정과 근거가 있으면 그 내용을 활용한다. 새로운 근거나 충돌이 발견되면 이번 판단에 미치는 영향을 설명한다.
- 기본적으로 가장 중요한 쟁점 하나부터 질문한다. 질문에는 근거와 미확인 사항, 답에 따라 달라지는 것을 짧게 담는다. 사용자가 정한 질문 순서를 우선한다.
- 사용자가 여러 질문을 함께 보고 싶어 하면 관련 질문을 묶어 제시한다. 전체 쟁점 목록을 요청하면 중요도와 함께 정리한다.
- 선택지가 판단에 도움이 되면 결과와 장단점을 덧붙인다. 추천안에는 근거와 가정을 밝힌다. 자료에 없는 현업 요구는 확인할 질문이나 임시 가정으로 표시한다.
- 답을 받으면 해결된 쟁점을 정리하고 남은 쟁점의 우선순위를 다시 판단한 뒤 다음 질문으로 이어간다. 새 쟁점도 현재 해결 방향과 계획에 미치는 영향으로 우선순위를 판단한다.
- 실행 가능성이 쟁점이면 작은 실행으로 확인할 동작, 조건과 성공 기준을 제안한다. 실제 실행 여부와 관찰 결과를 구분해 보고하고, 실행은 현재 요청이나 기존 승인 범위에서 진행한다.

## 4. 검토 마무리와 다음 작업 연결

- 사용자가 충분하다고 판단하거나 보류·종료를 요청하면 그 지점에서 마무리한다. 해결 방향, 필수 범위, 다음 작업과 확인 방법을 설명할 수 있으면 진행할 근거와 남은 쟁점을 짧게 제시한다.
- 마무리에는 유지하거나 바꾼 결정과 근거, 남은 가정·미확인 사항, 먼저 실행으로 확인할 항목을 필요한 만큼 남긴다.
- 문서 반영까지 요청받았으면 문제·규칙은 명세에, 기능 범위는 기능 목록에, 순서·확인 기준은 계획에, 중요한 결정 이유는 결정 기록에 반영한다. 변경은 사용자가 요청하거나 이미 승인한 범위에서 진행한다.
